Bowerbird Java Format

A Java formatter that arranges your code the way a bowerbird arranges its nest: carefully, and always the same way.

Get started GitHub Releases

Bowerbird is a modified version of palantir-java-format, which is itself based on google-java-format. Unlike most formatters, it isn't one fixed style: every formatting rule is a setting in a bowerbird.yml file, so a team can choose its own layout. Without a settings file you get Bowerbird's default style, whose output matches IntelliJ IDEA's formatter for the target code style.

Bowerbird is available under the Apache 2.0 License, the same licence as upstream. See NOTICE for attribution.

Install

Bowerbird is published to GitHub Packages under these coordinates:

ArtifactCoordinates
Formatterio.github.pieterjanscheir.bowerbird:bowerbird-java-format
SPIio.github.pieterjanscheir.bowerbird:bowerbird-java-format-spi
JDK bootstrapio.github.pieterjanscheir.bowerbird:bowerbird-java-format-jdk-bootstrap

GitHub Packages needs authentication, even for public packages. Create a personal access token (classic) with the read:packages scope and add the repository to your build:

repositories {
    mavenCentral()
    maven {
        url = 'https://maven.pkg.github.com/pieterjanscheir/bowerbird-java-format'
        credentials {
            username = providers.gradleProperty('gpr.user').orElse(providers.environmentVariable('GITHUB_ACTOR')).get()
            password = providers.gradleProperty('gpr.key').orElse(providers.environmentVariable('GITHUB_TOKEN')).get()
        }
    }
}

Put gpr.user and gpr.key in ~/.gradle/gradle.properties locally. In GitHub Actions, the built-in GITHUB_TOKEN works when the job has packages: read permission.

Every release also attaches the jars to its GitHub Release, if you prefer to download them.

Using it with Gradle

Module folders and Java packages (com.palantir.javaformat) are deliberately unchanged, so the upstream Gradle plugin can load Bowerbird. Apply the plugin and point it at Bowerbird instead of the default formatter:

plugins {
    id 'com.palantir.java-format' version '<upstream version Bowerbird is based on>'
}

dependencies {
    palantirJavaFormat 'io.github.pieterjanscheir.bowerbird:bowerbird-java-format:<bowerbird version>'
}

The plugin configures IntelliJ to use that formatter. For a command-line ./gradlew format task, add the com.palantir.baseline-format plugin. With Spotless, configure palantirJavaFormat() to use Bowerbird's artifact and run ./gradlew spotlessApply.

Do not enable the native formatter (palantir.native.formatter). It downloads Palantir's precompiled binary, which does not contain Bowerbird's rules.

Using it in IntelliJ IDEA

Install the upstream palantir-java-format IntelliJ plugin. It uses the formatter version that the Gradle plugin resolves for your project, so once the palantirJavaFormat dependency points at Bowerbird, import the project in IntelliJ or run:

./gradlew idea

Make sure the plugin is enabled under Settings → palantir-java-format Settings. Reformat Code then formats with Bowerbird.

Configuring the rules

Put a bowerbird.yml in a folder of its own, for example config/bowerbird/, and add that folder to the palantirJavaFormat dependencies next to Bowerbird:

dependencies {
    palantirJavaFormat 'io.github.pieterjanscheir.bowerbird:bowerbird-java-format:<bowerbird version>'
    palantirJavaFormat files('config/bowerbird')
}

Every setting is optional: list only what you want to change, and everything else keeps its default. For example, to keep Bowerbird's style but write if (x), indent by 2 spaces and keep the blank lines you type:

# config/bowerbird/bowerbird.yml
indent: 2
spaceAfterControlKeyword: true
blankLines:
  keepTyped: true

Starting from Palantir or Google style

If you like upstream palantir-java-format and only want to change a few things, start from a preset. preset: palantir sets every rule to what upstream does (it's tested against all of upstream's test cases), and the other settings in the file change it from there. For example, Palantir's style with 2-space indentation, which upstream can't do:

preset: palantir
indent: 2
continuationIndent: 4

The presets are bowerbird (the default), palantir (120 characters, 4-space indent, 8-space continuation) and google (upstream's Google style: like palantir, with 100 characters, 2-space indent and 4-space continuation).

On the command line

For pre-commit hooks, CI scripts and other tools that run the formatter directly, build the command-line launcher and pass the settings file with --config:

./gradlew :palantir-java-format:installDist
export JAVA_OPTS="$(for p in api code file parser tree util; do printf -- '--add-exports=jdk.compiler/com.sun.tools.javac.%s=ALL-UNNAMED ' $p; done)"
palantir-java-format/build/install/palantir-java-format/bin/palantir-java-format \
    --config bowerbird.yml --replace src/main/java/Example.java

The JAVA_OPTS line is needed on JDK 16 and later: the formatter uses the JDK's own Java parser, which the JDK only opens up with these flags. An invalid settings file stops with a one-line error and exit code 2.

--palantir without --config uses a bowerbird.yml on the classpath, or Bowerbird's defaults.

Gradle, Spotless and IntelliJ all load the formatter from the palantirJavaFormat dependencies, so they all read the same file; that's why the folder goes there. A few things to know:

  • Mistakes stop formatting. An unknown setting, a wrong type or invalid YAML fails with a message that names the setting and lists the valid ones, so a typo never goes unnoticed.
  • One file. If bowerbird.yml is on the formatter classpath more than once, formatting fails instead of guessing which one wins.
  • IntelliJ reads the file each time it formats, so edits apply on the next Reformat Code. Run ./gradlew idea or reload the Gradle project once after adding the folder.
  • Native formatter: the native-image formatter can't read a settings file. Leave palantir.native.formatter off.

All settings

The defaults are Bowerbird's own style. Each setting links to examples of what it changes.

SettingDefaultWhat it does
presetbowerbirdThe starting point for every other setting: bowerbird, palantir or google. See presets.
lineLength120Maximum line length. At least 40.
indent4Spaces per block indent.
continuationIndent4Spaces a wrapped line is indented by, relative to the line it continues. Upstream uses 8.
spaceAfterControlKeywordfalseif (x) when true, if(x) when false. Also for, while, switch, try, catch and synchronized. Example.
arrayInitializerBraceSpacestrue{ 1, 2 } when true, {1, 2} when false. Example.
closingParenOnOwnLinetrue) on its own line when parameters or arguments wrap one per line. When false, ) stays on the last line and a lambda passed as the last argument stays on the call's line: execute(account, () -> {. Example.
tryResourcesOnOwnLinestrueA try with several resources puts each one on its own line, with ( and ) on their own lines.
bodyWithoutBracesOnOwnLinetrueThe body of an if, for or while without braces always goes on its own line. When false, if (x) return; may stay on one line. Example.
blankLines.keepTypedfalseKeep the blank lines you type in code and between members, as upstream does. When false they are removed and only the rules below add blank lines. Example.
blankLines.aroundClassBodytrueOne blank line after a class header and before the class's closing brace.
blankLines.betweenFieldsfalseA blank line around each field, like around methods. When false, fields are listed without blank lines, also when they have JavaDoc.
blankLines.aroundFieldsWithJavadocfalseA blank line around each field that has JavaDoc, as upstream does, even when betweenFields is false.
blankLines.aroundInterfaceMethodsfalseA blank line around each method of an interface or annotation type.
imports.groups[static, java, javax, org, com, "*"]Import groups, in order. Each entry is a package prefix (java, com.example), static for all static imports, or "*" for everything else. An import goes in the group with the longest matching prefix; imports that match nothing go last. Example.
imports.blankLineBetweenGroupstrueA blank line between import groups.
javadoc.enabledtrueApply the JavaDoc settings below. When false, JavaDoc is left exactly as written. Example.
javadoc.removeBlankLinesInDescriptiontrueRemove blank lines inside the description. When false, paragraph breaks are kept (one blank line each).
javadoc.blankLineAfterDescriptiontrueOne blank line between the description and the first tag.
javadoc.blankLineAfterParamstrueOne blank line after the block of @param tags, when more tags follow.
javadoc.blankLineAfterReturntrueOne blank line after @return, when more tags follow.
javadoc.singleSpaceAfterTagNametrueExactly one space between a @param or @throws name and its description.

Default style

Without a bowerbird.yml, Bowerbird formats as shown below. Each rule is a setting you can change; the setting is named in brackets. Compared to upstream palantir-java-format:

  • No space between a control keyword and (: if(, for(, while(, switch(, try(, catch(, synchronized( (spaceAfterControlKeyword).
  • Imports in groups: static, java, javax, org, com, everything else, with a blank line between groups (imports).
  • Continuation indent of 4 spaces instead of 8 (continuationIndent).
  • ) on its own line when parameters or call arguments wrap one per line (closingParenOnOwnLine).
  • A space inside array initializer braces: { 1, 2, 3 } (arrayInitializerBraceSpaces).
  • The body of an if, for or while without braces always goes on its own line (bodyWithoutBracesOnOwnLine); one-line blocks are expanded.
  • Try with several resources: one resource per line (tryResourcesOnOwnLines).
  • Blank lines inside code are removed (blankLines.keepTyped); class bodies get one blank line after the header and before the closing brace (blankLines.aroundClassBody), one around methods and none between fields (blankLines.betweenFields).
  • JavaDoc tag blocks are separated by blank lines and tag names get a single space after them (javadoc); JavaDoc is never wrapped.

Wrapping

Continuation lines are indented by 4 spaces. When arguments are split one per line, the closing parenthesis goes on its own line. Method chains break before each ..

OrderResult result = orderService.placeOrderWithAVeryLongName(
    firstAccountArgument, secondInstrumentArgument, thirdQuantityArgument, fourth);

service.submit(
    builder.withAccount(firstAccountArgument)
        .withInstrument(secondInstrumentArgument)
        .build(),
    options,
    callback
);

executor.execute(
    account,
    () -> {
        run();
        run();
    }
);

List<String> symbols = orders.stream()
    .filter(order -> order.isOpen() && order.quantity() > minimumQuantity)
    .map(Order::symbol)
    .toList();

Blocks and statements

Before
public String name() { return "order"; }

void check(int x) {
    if (x > 0) return;
    if (x < 0) { x = 0; }
    Runnable r = () -> { run(); };
    Object o = new Object() { };
}
After
public String name() {
    return "order";
}

void check(int x) {
    if(x > 0)
        return;
    if(x < 0) {
        x = 0;
    }
    Runnable r = () -> {
        run();
    };
    Object o = new Object() {};
}

Empty bodies such as void empty() {} and static class Empty {} stay on one line.

Blank lines

Blank lines typed inside methods are removed, including before comments. Classes, interfaces and nested classes get one blank line after the header and before the closing brace. Fields have no blank lines between them, also when they have JavaDoc; methods, constructors, nested types and initializers get one around them. Interface methods have none. Enums have no blank line after the header or before the closing brace.

Before
class BlankLines {
    private int first;


    /** The second field. */
    private int second;
    BlankLines() {}
    void run() {

        int a = 1;

        // explains b
        int b = 2;

    }
}
After
class BlankLines {

    private int first;
    /** The second field. */
    private int second;

    BlankLines() {}

    void run() {
        int a = 1;
        // explains b
        int b = 2;
    }

}

JavaDoc

Blank lines inside the description are removed. One blank line follows the description, the @param block and @return. Parameter and exception names are followed by a single space. JavaDoc is never re-wrapped, so long lines stay as written.

Before
/**
 * Places an order on the exchange.
 *
 * Second paragraph of the description.
 * @param account   the client account
 * @param order the order to place
 * @return the placement result
 * @throws IllegalStateException when refused
 * @throws IllegalArgumentException   when invalid
 */
After
/**
 * Places an order on the exchange.
 * Second paragraph of the description.
 *
 * @param account the client account
 * @param order the order to place
 *
 * @return the placement result
 *
 * @throws IllegalStateException when refused
 * @throws IllegalArgumentException when invalid
 */

Building

You need JDK 21. The Gradle wrapper downloads everything else.

./gradlew :palantir-java-format:test

To try a local build in another project, publish it to Maven Local and add mavenLocal() to that project's repositories:

./gradlew :palantir-java-format-spi:publishToMavenLocal \
    :palantir-java-format-jdk-bootstrap:publishToMavenLocal \
    :palantir-java-format:publishToMavenLocal

CI runs ./gradlew build, which also runs Error Prone and the project's own format check, and fails when the build changes tracked files.

Adding a formatting rule

  1. Add a YourRule.input and YourRule.output pair to palantir-java-format/src/test/resources/com/palantir/javaformat/java/bowerbird-testdata/. BowerbirdIntegrationTest picks them up.
  2. Add the setting to BowerbirdRules (with its default) and to the table in BowerbirdConfig, so bowerbird.yml can set it.
  3. Change the formatter, usually in JavaInputAstVisitor.java, behind rule(BowerbirdRules::yourSetting), so upstream styles and their tests are unaffected.
  4. To test the non-default value, add a YourRule.yml next to the input and output files; BowerbirdIntegrationTest applies it to that test case.
  5. Run the tests. ./gradlew test -Drecreate=true regenerates the expected outputs, so review that diff carefully.
  6. Check the output against IntelliJ's formatter with the target code style: IntelliJ should leave Bowerbird's output unchanged.

Keep one rule per commit, so upstream merge conflicts are easy to trace.

Staying up to date with upstream

A weekly workflow opens a pull request when palantir-java-format publishes a new release, or an issue when the merge conflicts. You can also run it by hand from the Actions tab for a specific upstream tag or branch. To merge by hand:

git fetch upstream
git merge upstream/develop

README.md conflicts on every upstream change to it: keep Bowerbird's version and apply upstream's changes to docs/upstream-README.md if they matter.

Releasing

Push a version tag to build, test and publish that version. The version is taken from the tag.

git tag 1.0.0
git push origin 1.0.0

The release workflow publishes the formatter, SPI and JDK bootstrap to GitHub Packages and creates a GitHub Release with the jars and generated release notes.
