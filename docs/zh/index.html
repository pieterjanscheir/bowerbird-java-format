Bowerbird Java Format

一款 Java 格式化工具，像园丁鸟（bowerbird）布置巢穴那样整理你的代码：一丝不苟，而且始终如一。

快速开始 GitHub 版本发布

Bowerbird 是 palantir-java-format 的修改版，而后者本身又基于 google-java-format。与大多数格式化工具不同，它并不是一套固定的风格：每条格式化规则都是 bowerbird.yml 文件中的一个配置项，团队可以自行决定代码布局。没有配置文件时，使用的是 Bowerbird 的默认风格，其输出与 IntelliJ IDEA 格式化器在目标代码风格下的结果一致。

Bowerbird 采用与上游相同的 Apache 2.0 许可证。署名信息见 NOTICE。

安装

Bowerbird 发布在 GitHub Packages 上，坐标如下：

构件坐标
格式化器io.github.pieterjanscheir.bowerbird:bowerbird-java-format
SPIio.github.pieterjanscheir.bowerbird:bowerbird-java-format-spi
JDK 引导模块io.github.pieterjanscheir.bowerbird:bowerbird-java-format-jdk-bootstrap

即使是公开包，GitHub Packages 也需要认证。请创建一个带有 read:packages 权限范围的个人访问令牌（classic），并把该仓库添加到构建中：

repositories {
    mavenCentral()
    maven {
        url = 'https://maven.pkg.github.com/pieterjanscheir/bowerbird-java-format'
        credentials {
            username = providers.gradleProperty('gpr.user').orElse(providers.environmentVariable('GITHUB_ACTOR')).get()
            password = providers.gradleProperty('gpr.key').orElse(providers.environmentVariable('GITHUB_TOKEN')).get()
        }
    }
}

在本地，把 gpr.user 和 gpr.key 写入 ~/.gradle/gradle.properties。在 GitHub Actions 中，只要作业拥有 packages: read 权限，内置的 GITHUB_TOKEN 即可使用。

每个版本也会把 jar 包附加到对应的 GitHub Release 上，方便直接下载。

在 Gradle 中使用

模块目录和 Java 包名（com.palantir.javaformat）有意保持不变，这样上游的 Gradle 插件就能加载 Bowerbird。应用该插件，并让它使用 Bowerbird 而不是默认的格式化器：

plugins {
    id 'com.palantir.java-format' version '<upstream version Bowerbird is based on>'
}

dependencies {
    palantirJavaFormat 'io.github.pieterjanscheir.bowerbird:bowerbird-java-format:<bowerbird version>'
}

该插件会配置 IntelliJ 使用这个格式化器。如需命令行的 ./gradlew format 任务，请添加 com.palantir.baseline-format 插件。如果使用 Spotless，请将 palantirJavaFormat() 配置为使用 Bowerbird 的构件，然后运行 ./gradlew spotlessApply。

不要启用原生格式化器（palantir.native.formatter）。它会下载 Palantir 预编译的二进制文件，其中不包含 Bowerbird 的规则。

在 IntelliJ IDEA 中使用

安装上游的 palantir-java-format IntelliJ 插件。它使用 Gradle 插件为项目解析出的格式化器版本，因此只要 palantirJavaFormat 依赖指向 Bowerbird，在 IntelliJ 中导入项目或运行以下命令即可：

./gradlew idea

请确认已在 Settings → palantir-java-format Settings 中启用该插件。之后 Reformat Code 就会使用 Bowerbird 进行格式化。

配置规则

把 bowerbird.yml 放在一个单独的目录中，例如 config/bowerbird/，然后把该目录与 Bowerbird 一起加入 palantirJavaFormat 依赖：

dependencies {
    palantirJavaFormat 'io.github.pieterjanscheir.bowerbird:bowerbird-java-format:<bowerbird version>'
    palantirJavaFormat files('config/bowerbird')
}

所有配置项都是可选的：只需列出想要修改的项，其余均保持默认值。例如，保留 Bowerbird 的风格，但写成 if (x)、使用 2 个空格缩进，并保留你输入的空行：

# config/bowerbird/bowerbird.yml
indent: 2
spaceAfterControlKeyword: true
blankLines:
  keepTyped: true

以 Palantir 或 Google 风格为起点

如果你喜欢上游 palantir-java-format 的风格，只想改动少数几处，可以从预设开始。preset: palantir 会把每条规则都设为上游的行为（已通过上游全部测试用例的验证），文件中的其他配置项再在此基础上进行调整。例如，使用 2 空格缩进的 Palantir 风格，这是上游做不到的：

preset: palantir
indent: 2
continuationIndent: 4

可用的预设有 bowerbird（默认）、palantir（120 个字符、4 空格缩进、8 空格续行缩进）和 google（上游的 Google 风格：与 palantir 类似，但为 100 个字符、2 空格缩进、4 空格续行缩进）。

在命令行中使用

对于 pre-commit 钩子、CI 脚本以及其他直接运行格式化器的工具，请构建命令行启动器，并通过 --config 传入配置文件：

./gradlew :palantir-java-format:installDist
export JAVA_OPTS="$(for p in api code file parser tree util; do printf -- '--add-exports=jdk.compiler/com.sun.tools.javac.%s=ALL-UNNAMED ' $p; done)"
palantir-java-format/build/install/palantir-java-format/bin/palantir-java-format \
    --config bowerbird.yml --replace src/main/java/Example.java

在 JDK 16 及更高版本上需要 JAVA_OPTS 这一行：格式化器使用 JDK 自带的 Java 解析器，而 JDK 只有在加上这些参数时才会开放它。配置文件无效时，会输出一行错误信息并以退出码 2 结束。

只指定 --palantir 而不指定 --config 时，会使用 classpath 上的 bowerbird.yml；如果没有，则使用 Bowerbird 的默认值。

Gradle、Spotless 和 IntelliJ 都从 palantirJavaFormat 依赖中加载格式化器，因此读取的是同一个文件；这正是要把该目录放在那里的原因。需要注意以下几点：

  • 配置错误会中止格式化。未知的配置项、错误的类型或无效的 YAML 都会导致失败，错误信息会指出出错的配置项并列出所有有效配置项，因此拼写错误不会被忽略。
  • 只能有一个文件。如果格式化器的 classpath 上出现多个 bowerbird.yml，格式化会直接失败，而不会去猜测应该以哪个为准。
  • IntelliJ 每次格式化时都会读取该文件，因此修改会在下一次 Reformat Code 时生效。添加该目录后，请运行一次 ./gradlew idea 或重新加载 Gradle 项目。
  • 原生格式化器：native-image 格式化器无法读取配置文件。请保持 palantir.native.formatter 关闭。

全部配置项

默认值即 Bowerbird 自身的风格。每个配置项都链接到展示其效果的示例。

配置项默认值作用
presetbowerbird其他所有配置项的起点：bowerbird、palantir 或 google。参见预设。
lineLength120最大行宽，不能小于 40。
indent4每级代码块缩进的空格数。
continuationIndent4换行后的续行相对于其所接续的行缩进的空格数。上游使用 8。
spaceAfterControlKeywordfalse为 true 时写作 if (x)，为 false 时写作 if(x)。同样适用于 for、while、switch、try、catch 和 synchronized。示例。
arrayInitializerBraceSpacestrue为 true 时写作 { 1, 2 }，为 false 时写作 {1, 2}。示例。
closingParenOnOwnLinetrue当形参或实参按每行一个换行时，) 单独占一行。为 false 时，) 留在最后一行，作为最后一个实参传入的 lambda 也留在调用所在的行：execute(account, () -> {。示例。
tryResourcesOnOwnLinestrue包含多个资源的 try 语句中，每个资源各占一行，( 和 ) 也各自单独占一行。
bodyWithoutBracesOnOwnLinetrue不带花括号的 if、for 或 while 语句体总是另起一行。为 false 时，if (x) return; 可以保持在同一行。示例。
blankLines.keepTypedfalse与上游一样，保留你在代码中和成员之间输入的空行。为 false 时这些空行会被删除，只由下面的规则添加空行。示例。
blankLines.aroundClassBodytrue在类声明头之后和类的右花括号之前各保留一个空行。
blankLines.betweenFieldsfalse像方法一样，在每个字段前后添加空行。为 false 时，字段之间不留空行，即使字段带有 JavaDoc 也是如此。
blankLines.aroundFieldsWithJavadocfalse与上游一样，在每个带 JavaDoc 的字段前后添加空行，即使 betweenFields 为 false。
blankLines.aroundInterfaceMethodsfalse在接口或注解类型的每个方法前后添加空行。
imports.groups[static, java, javax, org, com, "*"]按顺序排列的导入分组。每一项可以是包名前缀（java、com.example）、表示所有静态导入的 static，或表示其余所有导入的 "*"。每个导入归入前缀匹配最长的分组；没有任何匹配的导入放在最后。示例。
imports.blankLineBetweenGroupstrue在导入分组之间添加空行。
javadoc.enabledtrue应用下面的 JavaDoc 配置项。为 false 时，JavaDoc 完全保持原样。示例。
javadoc.removeBlankLinesInDescriptiontrue删除描述部分内的空行。为 false 时保留段落分隔（每处一个空行）。
javadoc.blankLineAfterDescriptiontrue在描述与第一个标签之间保留一个空行。
javadoc.blankLineAfterParamstrue当后面还有其他标签时，在 @param 标签块之后保留一个空行。
javadoc.blankLineAfterReturntrue当后面还有其他标签时，在 @return 之后保留一个空行。
javadoc.singleSpaceAfterTagNametrue@param 或 @throws 的名称与其描述之间恰好保留一个空格。

默认风格

没有 bowerbird.yml 时，Bowerbird 按如下方式格式化。每条规则都是一个可以修改的配置项，括号中注明了对应的配置项。与上游 palantir-java-format 相比：

  • 控制关键字与 ( 之间没有空格：if(、for(、while(、switch(、try(、catch(、synchronized(（spaceAfterControlKeyword）。
  • 导入按分组排列：静态导入、java、javax、org、com、其余所有导入，分组之间空一行（imports）。
  • 续行缩进为 4 个空格，而不是 8 个（continuationIndent）。
  • 当形参或调用实参按每行一个换行时，) 单独占一行（closingParenOnOwnLine）。
  • 数组初始化器的花括号内侧留空格：{ 1, 2, 3 }（arrayInitializerBraceSpaces）。
  • 不带花括号的 if、for 或 while 语句体总是另起一行（bodyWithoutBracesOnOwnLine）；写在一行内的代码块会被展开。
  • 包含多个资源的 try 语句：每行一个资源（tryResourcesOnOwnLines）。
  • 删除代码内部的空行（blankLines.keepTyped）；类体在声明头之后和右花括号之前各有一个空行（blankLines.aroundClassBody），方法前后各有一个空行，字段之间没有空行（blankLines.betweenFields）。
  • JavaDoc 的标签块之间以空行分隔，标签名后只保留一个空格（javadoc）；JavaDoc 从不自动换行。

续行缩进 4 个空格。当实参拆分为每行一个时，右括号单独占一行。方法链在每个 . 之前换行。

OrderResult result = orderService.placeOrderWithAVeryLongName(
    firstAccountArgument, secondInstrumentArgument, thirdQuantityArgument, fourth);

service.submit(
    builder.withAccount(firstAccountArgument)
        .withInstrument(secondInstrumentArgument)
        .build(),
    options,
    callback
);

executor.execute(
    account,
    () -> {
        run();
        run();

);

List<String> symbols = orders.stream()

    .map(Order::symbol)
    .toList();

格式化后
public String name() {
    return "order";
}

    if(x > 0)
        return;
    if(x < 0) {
        x = 0;
    }
    Runnable r = () -> {
        run();
    };
    Object o = new Object() {};
}

空的主体，例如 void empty() {} 和 static class Empty {}，保持在一行内。

空行

方法内部输入的空行会被删除，注释前的空行也不例外。类、接口和嵌套类在声明头之后和右花括号之前各有一个空行。字段之间没有空行，即使字段带有 JavaDoc 也是如此；方法、构造器、嵌套类型和初始化块前后各有一个空行。接口方法之间没有空行。枚举在声明头之后和右花括号之前都没有空行。

格式化前
class BlankLines {
    private int first;


    /** The second field. */
    private int second;
    BlankLines() {}
    void run() {

        int a = 1;

        // explains b
        int b = 2;

    }
}
格式化后
class BlankLines {

    private int first;
    /** The second field. */
    private int second;

    BlankLines() {}

    void run() {
        int a = 1;
        // explains b
        int b = 2;
    }

}

JavaDoc

描述部分内的空行会被删除。描述、@param 块和 @return 之后各跟一个空行。参数名和异常名后只保留一个空格。JavaDoc 从不重新换行，因此长行保持原样。

格式化前
/**
 * Places an order on the exchange.
 *
 * Second paragraph of the description.
 * @param account   the client account
 * @param order the order to place
 * @return the placement result
 * @throws IllegalStateException when refused
 * @throws IllegalArgumentException   when invalid
 */
格式化后
/**
 * Places an order on the exchange.
 * Second paragraph of the description.
 *
 * @param account the client account
 * @param order the order to place
 *
 * @return the placement result
 *
 * @throws IllegalStateException when refused
 * @throws IllegalArgumentException when invalid
 */

构建

需要 JDK 21，其余依赖都由 Gradle wrapper 自动下载。

./gradlew :palantir-java-format:test

如需在其他项目中试用本地构建，请将其发布到 Maven Local，并在该项目的仓库列表中添加 mavenLocal()：

./gradlew :palantir-java-format-spi:publishToMavenLocal \
    :palantir-java-format-jdk-bootstrap:publishToMavenLocal \
    :palantir-java-format:publishToMavenLocal

CI 会运行 ./gradlew build，其中还包括 Error Prone 和项目自身的格式检查；如果构建修改了已跟踪的文件，CI 会失败。

添加格式化规则

  1. 在 palantir-java-format/src/test/resources/com/palantir/javaformat/java/bowerbird-testdata/ 中添加一对 YourRule.input 和 YourRule.output 文件，BowerbirdIntegrationTest 会自动识别它们。
  2. 把该配置项（连同默认值）添加到 BowerbirdRules，并加入 BowerbirdConfig 中的映射表，这样 bowerbird.yml 就能设置它。
  3. 修改格式化器（通常在 JavaInputAstVisitor.java 中），并用 rule(BowerbirdRules::yourSetting) 进行控制，以免影响上游风格及其测试。
  4. 如需测试非默认值，请在输入和输出文件旁添加 YourRule.yml；BowerbirdIntegrationTest 会将其应用到该测试用例。
  5. 运行测试。./gradlew test -Drecreate=true 会重新生成预期输出，因此请仔细检查由此产生的 diff。
  6. 使用目标代码风格，将输出与 IntelliJ 格式化器的结果进行对照：IntelliJ 不应改动 Bowerbird 的输出。

每次提交只包含一条规则，这样与上游合并时出现的冲突更容易追溯。

与上游保持同步

每周运行的工作流会在 palantir-java-format 发布新版本时创建一个 pull request；如果合并出现冲突，则创建一个 issue。你也可以在 Actions 标签页中针对特定的上游标签或分支手动运行它。手动合并的方法如下：

git fetch upstream
git merge upstream/develop

上游每次修改 README.md 都会产生冲突：请保留 Bowerbird 的版本；如果上游的改动有意义，再把它们应用到 docs/upstream-README.md。

发布

推送一个版本标签即可构建、测试并发布该版本，版本号取自标签。

git tag 1.0.0
git push origin 1.0.0

发布工作流会把格式化器、SPI 和 JDK 引导模块发布到 GitHub Packages，并创建一个包含 jar 包和自动生成的发布说明的 GitHub Release。

Bowerbird 是 palantir-java-format 和 google-java-format 的分支，采用 Apache 2.0 许可证。 本页面由 docs/zh/index.html 构建，是英文页面的翻译版本。
